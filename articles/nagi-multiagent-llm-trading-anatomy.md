「AIが自動で稼ぐ」——この手の話の9割は中身が無い。だからこの記事では儲け話を一切しない。代わりに、**ローカルLLM（クラウドの有料APIに依存しない小型モデル）だけで動く自律取引システムを、実際にどう設計・実装したか**を、動いているコードの構造そのままに解剖する。題材は筆者が build-in-public で開発中の `Nagi（凪）`。デモ口座で動く研究システムであって、投資商品ではない。

読んで得られるのは「勝てるシグナル」ではなく、**「複数のLLMエージェントを安全に協調させ、外部市場という極度に動的な対象へ接続する設計パターン」**だ。取引に興味がなくても、自律エージェント基盤を作る人にはそのまま転用できる。

## なぜ「マルチエージェント × 多段ゲート」なのか

LLMを取引に使うとき、素朴に「1個のLLMに『買う？売る？』と聞く」と必ず破綻する。理由は3つ:

1. **1つのモデルに全責務を負わせると幻覚がそのまま発注になる**。テクニカル判断・ニュース解釈・最終意思決定は関心が違う。混ぜると検証も改善もできない。
2. **LLMの出力をそのまま信じてはいけない**。確率的なテキスト生成器に、不可逆な発注の最終権限を渡すのは設計ミス。
3. **市場は動的で、モデルは静的**。学習時点の分布から外れた相場で、モデルは自信満々に間違える。

Nagi の答えは **「関心で分割したエージェント群（Agent A/B/C/D）」+「ルール層による多段安全ゲート」** の二層構造だ。LLMは"助言者"、最終的な発注可否は決定論的なルールが持つ。**賢いコードより、検証可能なコード**を選ぶ。

## アーキテクチャ全体像

```
MT5（市場データ） → 並列ストラテジープラグイン群 → 統合分析パイプライン(Agent A/B/C)
   → 多段安全ゲート(6段) → MT5発注 → SQLite永続化
            ↑                                    ↓
   自律監視ループ(SystemMonitor) ← Agent D(品質診断) ← 取引結果フィードバック
```

データは MetaTrader5 からマルチタイムフレーム（D1/H4/M15）で入り、複数の戦略プラグインが並列で指標計算と一次判定を行う。そこから先が本題の「LLMエージェント協調」と「安全ゲート」だ。

### Agent A/B/C/D — 関心で分割したLLMエージェント

| Agent | 役割 | なぜ分けるか |
|:--|:--|:--|
| **A** | テクニカル分析（price action・指標） | 数値パターンの解釈に特化。ニュースの文脈は持たせない |
| **B** | ニュース分析（GDELT 感情スコア） | 言語・イベント解釈に特化。チャートは見ない |
| **C** | 統合判定（A/B の結果 + 戦略プロファイルを統合） | "意思決定"だけを担う。入力は他エージェントの構造化出力 |
| **D** | サイクル品質診断・再訓練要求 | 取引結果を事後評価し、システム自身の劣化を検出する"監査役" |

設計上の肝は、**A/B/C を「Chain of Responsibility」パイプラインとして逐次実行**し、各ステップ間の文脈を `ContextProvider` という単一の Protocol で注入していること。エージェントを足す/差し替えるときに呼び出し側を書き換えずに済む。エージェント協調の典型的なアンチパターン（巨大な if 分岐で各エージェントを叩く）を避け、ステップの合成で表現する。

そして Agent D が重要だ。多くの「AIエージェントシステム」は作りっぱなしで、**自分の判断が劣化していることに気づけない**。Nagi は取引サイクルごとに D が品質指標を評価し、必要なら閾値調整や再訓練を要求する自己診断ループを持つ。ただし D も"助言者"であり、安全停止の最終権限はルール層が握る——この権限分離が肝。

### ローカルLLMで動かす（有料APIゼロ）

推論バックエンドは3系統を config 1行で切り替えられる:

- `llama_cpp`（llama-server を複数インスタンス）
- `tabby_api`（ExLlamaV2 + LoRA 動的切替）
- `direct`（transformers + PEFT 直接ロード）

各 Agent が消費するのは、**汎用大型モデルではなく、用途特化に蒸留した小型 LoRA アダプタ**（姉妹プロジェクト `Bonsai` が生成）。「データセンターに大型 teacher、手元に小型 student」という2026年の主流パターンを、取引ドメインで実装したものだ。クラウドの有料 API を一切叩かずに、テクニカル/ニュース/統合の各タスクへ特化したモデルを当てる。

### 6段の安全ゲート — LLMに発注の最終権限を渡さない

統合判定（Agent C）がシグナルを出しても、それは"提案"に過ぎない。発注に至るには決定論的な6段ゲートを全通過する:

1. **HOLD 判定**: AIが「様子見」と言ったものを除外
2. **既存ポジション**: 同一シンボルの重複保有をブロック
3. **エントリークールダウン**: 過剰な連続エントリーを防止
4. **MTF 整合**: ダウ理論バイアス（H4）と実行足（M15）の方向整合
5. **信頼度閾値**: 一定未満の確信度を排除
6. **TP/SL 妥当性**: 利確・損切り価格が論理的に正しいか（BUY なら TP>現在価格>SL 等）を検証

この「LLMは助言、ルールが最終決定」という分離が、幻覚を発注事故にしないための核心だ。

### ダウ理論フィルタ — 古典を構造化して機械に持たせる

エージェントの判断に加え、`市場構造（ダウ理論）`フィルタが上位足のトレンドバイアスを判定し、それと逆行するシグナルをブロックする。LLMの確率的判断に、**人間のトレーダーが使う構造的フレームを機械可読な制約として重ねる**——これも「LLM単独を信じない」設計思想の現れ。

## build-in-public の正直な現在地

ここがこの記事の一番大事な部分だ。**この種のシステムで成果を盛るのは簡単で、だからこそ盛らない。**

- これは**デモ口座での研究段階**であり、実利益を主張しない。
- 過去のバックテストでは、ある戦略・通貨ペア・期間の組み合わせで**取引がほとんど発生しない**という問題にぶつかった（パイプラインの調整課題）。こうした「動かない」もログに残して公開していく。
- forecast 系のモデルは未学習の部分があり、現状は古典的なベースライン（ARIMA）で代替している箇所がある。

なぜ失敗を書くのか。AI取引は規制当局（CFTCなど）が名指しで詐欺警告するカテゴリで、実績を盛った広告で溢れている。**だからこそ「動かない部分を含めて構造を見せる」ことそのものが、技術者にとっての価値であり信頼**だと考えている。儲かるかではなく、**どう作ってあるか**を見てほしい。

## 転用できる設計パターン（取引以外でも）

この記事を取引の文脈を外して読むと、汎用的な自律エージェント設計のチェックリストになる:

- **関心でエージェントを分割**し、巨大分岐でなく Chain of Responsibility で合成する
- **LLMは助言者、不可逆な行動の最終決定は決定論的ルール層**に持たせる
- **自己診断エージェント（監査役）**でシステム自身の劣化を検出する
- **用途特化の小型ローカルモデル**でコストと依存を下げる
- **失敗を含めて build-in-public** で出し、信頼を技術で作る
