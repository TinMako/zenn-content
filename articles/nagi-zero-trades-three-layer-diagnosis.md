## 発見: 14日で約定4件

筆者が開発している自律FX取引システム `Nagi（凪）` は、複数のローカルLLMエージェントが協調してテクニカル分析・ニュース分析・統合判定を行い、決定論的な多段ゲートを通過したものだけを発注する構成になっている。詳しい構造は[過去記事](https://zenn.dev/tinmako/articles/nagi-autonomous-fx-agent-design)に譲るとして、今回は運用中に踏んだ障害の話をする。

デモ口座の状況を隠さずに書く。入金100万円に対し現在の口座残高は695,185円、**通算-30.5%**。直近7日の増減は+1,383円とほぼ横ばい。損切りと利確を合わせた勝率は238勝563敗（29.7%）で、方向整合が取れたクリーンな取引だけを集計しても実現損益は-15,666円——戦略そのものは今もネットで負けている。この記事はその戦略の当否を語るものではない。もっと手前、**「そもそもLLMエージェントが判断を返せていない」**という、取引ロジック以前のインフラ障害の話だ。

異常に最初に気づいたのは取引頻度だった。過去の稼働実績では1日5〜20件の約定があったのに、直近14日間の約定はわずか4件（6/27, 7/2, 7/6, 7/7）。エージェントが「HOLD」を返しているならまだ健全だが、ログを見るとそうではなかった。**エージェントがJSONそのものを返せず、パイプラインが暗黙のフォールバック値で処理を継続していた**。

日次の平均信頼度（avg_confidence）を追うと、6/29〜30は0.057〜0.072という異常値まで落ち込んでいた（発注ゲートの閾値は0.60）。これは「自信のない判断」ではなく、**JSON解析に失敗し続けた結果、システムがゼロに近い確信度で埋め合わせていた**ことを意味する。

この日、三者会議形式（本セッションの推論 + `codex exec` + `agy` の独立レビュー3系統）で丸1日かけて診断した結果、原因は独立した3層に分かれていた。それぞれ仮説→実験→確定の順で追う。

## 診断層1: char→token換算係数の算術不足

### 仮説

直近のPR（#280、7/3マージ）で `input_token_budget`（トークン予算によるプロンプトトリム機構）を有効化したはずだった。それでも7/6に386件、7/7に170件のcontext-exceededエラーが発生し続けている。7/8朝08:38に再起動して設定の読み込みを確認したにもかかわらず、08:46には早くも再発した。フラグは有効なのに効いていない——ということは、トリムの**判定式そのものが間違っている**可能性が高い。

### 実験

トリム判定は「プロンプトの文字数 × `chars_per_token` 係数」で見積もりトークン数を計算し、予算（9,945トークン相当）を超えたら削る、という単純な仕組みだった。既定の `chars_per_token` は1.4（= 1トークンあたり約0.714文字、日本語は英語よりトークン効率が良いという経験則の反映のつもりだった）。

これを実測で検証するため、llama-serverの `/tokenize` エンドポイントに実際のプロンプト断片を投げてトークン数を数えた。

```bash
curl -s http://127.0.0.1:8083/tokenize \
  -H "Content-Type: application/json" \
  -d '{"content": "<日本語の実プロンプト断片>"}' | jq '.tokens | length'
```

結果は日本語の平文で **0.816 tok/char**、希少漢字が混じる文面では **0.982 tok/char**。つまり1文字がほぼ1トークンに近い。仮定していた0.714 tok/charとは**最大で1.4倍近いずれ**があった。文字数ベースの予算（9,945文字）はこの係数のずれのぶんだけ「予算内」と誤判定し続け、実際のトークン数は予算を超過したままcontext-exceededに到達していた。証拠として、トリム機構が発火した形跡はログ上一度もなかった——**文字数判定では常に「予算内」に見えていた**からだ。

### 確定

`chars_per_token` を1.4→**1.0**（1文字=1トークン相当という安全側の仮定）へ厳格化する修正をPR #283としてまとめた。併せて、修正の効果を実データで検証できるように `ai_llm_prompt_input_trim_total{expert_type,action}` というCounterメトリクスを新設した（`action=news_shrink` / `tail_truncate`）。これは会議で `codex exec` によるレビューが出した条件——「係数を変えるだけでなく、実payloadで効果を検証できる観測点を必ず付けること」——への対応でもある。

係数の選定でも独立レビュー3系統の意見は割れた。もう一方の独立レビュー（`agy`）は「byte-fallbackの病的ケースを考慮して0.8まで下げるべき」と主張したが、これは`codex`の反証で棄却された。通常のニュース文で1文字あたり3トークン相当を仮定するのは非現実的で、0.8まで下げると毎リクエストでトリムが発火し、トリムしすぎによる情報欠落という別の二次災害を招く。最終的に1.0への厳格化 + 観測カウンタで着地した。

反映後（14:18 pm2 restart）の効果は明確だった。トリムカウンタが発火し始め（`news_shrink`/`tail_truncate`）、直後のサイクル（14:25）でavg_confidenceが**0.732 / 0.660**——数週間ぶりにゲート閾値0.60を突破した。ただしcontext-exceededは57件/日相当まで激減したものの完全にはゼロにならず、14:25にも4件のバーストが残った。これは次の層（KVキャッシュ枯渇）の残存分であり、層1単独では根治しきれないことがここで判明する。

## 診断層2: KVキャッシュ枯渇と入力長超過は別のエラー

### 仮説

500エラー「Context size has been exceeded.」は文字通り「入力が長すぎる」という意味だと最初は考えていた。層1の係数修正でトークン予算判定は正確になったはずなのに、なぜまだ発火するのか。

### 実験

llama.cppのソース（`server-context.cpp`）を確認すると、**この500エラーは`llama_decode`が`ret=1`を返した場合、つまりKVキャッシュ（推論の途中状態を保持するメモリ領域）の枯渇時に発生する**ものだった。一方、リクエストの入力トークン数がコンテキストサイズを単純に超えた場合は、別の400エラー「request exceeds the available context size」が返る。この2つは似て非なるエラーで、原因も対処も異なる。

単発リクエストで実験した限りでは、8,101トークンまでは200 OKが返り、生成が黙って途中で切り詰められることを確認した（プロンプト7,800トークンに対しcompletionは383トークンで打ち切り）。つまり単発では8,192トークンの上限までなだらかに劣化するだけで、500エラーには至らない。500エラーが再現するのは、**本番同様の連続リクエストパターン + ハイブリッド構造のモデル（LFM2.5）** の組み合わせだった。KVキャッシュは単発では枯渇せず、連続稼働でのメモリ管理の積み残しが真因という切り分けができた。

### 確定

この層は「入力を削る」対症療法では根治できない。500エラーの原因がKVキャッシュ側にある以上、**モデルそのものの構造を変える**必要がある——というのが次の層3への橋渡しになった。層1の係数修正はcontext-exceeded全体を大きく減らしたが、ゼロにはできなかった理由がここにある。

## 診断層3: json_schema grammar と Thinking系モデルは全サイズで非互換

### 仮説

`ai_llm_parse_failure_total{sentiment,no_json}` というメトリクスが累計**4,981件**まで積み上がっていた。加えて `think_tag_stripped`（`<think>`タグを剥がして再試行した回数）が4,328件。これはプロンプトが長すぎて起きているのではなく、**モデルの出力形式そのものが構造化出力の仕組みと衝突している**のではないかという仮説が浮上した。

### 実験

実際のsystem prompt + agent_cの本番JSONスキーマで再現実験を行うと、プロンプトが通常サイズ（5.9kトークン、予算的には全く問題ないサイズ）であっても、**500エラー「Failed to parse input at pos 0: `<think>`」が発生した**。

原因は、当時agent_c（strategist）が使っていたモデル `LFM2.5-1.2B-Thinking` の推論の癖にあった。Thinking系モデルは応答の冒頭に`<think>...</think>`という思考過程を出力する。しかしllama-serverの`json_schema` grammar（応答をJSON文法に強制する仕組み）は、応答の先頭がJSON文法に従うことを前提にしている。`<think>`タグはこの文法に違反するため、**grammar制約が「文法違反」としてリクエストを即座に拒否する**。

クライアント側の実装は、このgrammarエラーを受けて「grammarを外してリトライする」というフォールバックを持っていた。これが二次被害を生んだ。grammarなしで再試行すると、モデルは制約なく`<think>...</think>`を出力し続け、その思考トークンが`max_tokens`（768トークン）を食い潰してしまい、**肝心のJSON本体が生成される前にトークン予算が尽きる**。結果、`no_json`のパース失敗としてカウントされる。累計4,981件はこの経路の帰結だった。

この症状には既視感があった。姉妹エージェント agent_d が2026-06-25に踏んだ「36日間の空出力回帰」も、モデルのbase選定（Thinking系 + 非CoTデータの不整合）が原因だった。今回のagent_cも同型の疾患であり、**対症療法（grammarを外す・few-shotで書式を補強する）を積み増すのではなく、base選定そのものを直す**のが唯一の根治だと判断した。

### 確定

幸い、この根治は既に別チームによって設計・実装済みだった。姉妹プロジェクトBonsai（LLM蒸留基盤）側のPR #46（7/3マージ）で、strategist（agent_c）のbaseモデルを **LFM2.5-1.2B-Thinking → Gemma 4 E2B it（非thinking）** へ切り替える設計と実装が完了していた。未完だったのは「再学習の実行 + GGUF生成 + Nagi側のデプロイ」という最後の配線だけだった（このとき稼働していたGGUFファイルは5/20生成のLFM2.5サイズ・697MBのままだった）。

## 移行編: Gemma 4 デプロイで踏んだ4つの罠

根治策自体は明確だった。しかし「再学習を実行してGGUFを差し替える」だけの作業のはずが、実際にやってみると4つの罠が連続して現れた。

### 罠1: peft の ClippableLinear 非対応（Bonsai #46 は初回実行で即死する状態だった）

LoRAの対象モジュール（`lora.target_modules`）を裸の名前リストで指定していたところ、Gemma 4はマルチモーダル構成のため vision/audio 塔に `Gemma4ClippableLinear` という層が存在し、これがモジュール名のパターンにマッチしてしまっていた。peft 0.19時点ではこの層に対するLoRA適用が未対応（[peft#3129](https://github.com/huggingface/peft/issues/3129)）で、そのまま実行すると即座に失敗する。

対処は、対象を言語塔限定のregexパターンへ絞り込むこと（Bonsai #47）。実機で205モジュールがヒットし、`ClippableLinear`は0件であることを確認してから再学習を実行した。「GGUFが5/20から更新されていなかった」真因の一つは、週末学習が走ってもこのエラーで毎回失敗していた可能性が高い、という発見でもあった。

再学習自体は無事完走: train_loss 1.127 / token accuracy 0.96 / 292秒（100例）。

### 罠2: merge 時の `--base-model` 明示漏れ

LoRAアダプタをbaseモデルへマージするステップで、アダプタ名から使用すべきbaseモデルを自動推定する処理があったが、これが外れて誤ったbaseにフォールバックする挙動を発見した。`--base-model` を明示的に指定することで回避。マージ後、GGUF（q4_K_M量子化、3.26GB）を生成した。

### 罠3: 配信バイナリのアーキ未対応

生成したGGUFを既存のllama-serverバイナリ（b8232）にロードしようとしたところ、**Gemma 4アーキテクチャ自体に対応していない**バイナリだった。公式ビルドb9910（CUDA 12.4）を別ディレクトリへ新規導入し、旧LFM2.5用GGUFの後方互換も実機で確認した上で切り替えた。

### 罠4: Gemma 4 は既定でthinkingし、max_tokensを食い潰す

新バイナリ+新GGUFで動作確認したところ、応答の`content`が空、`reasoning_content`側に768トークンが詰まっているという現象に遭遇した。**Gemma 4は既定で思考過程を出力するモデルであり**、学習データ（非thinkingで蒸留したもの）とサービング設定の不整合が起きていた。

対処は起動オプションに `--reasoning-budget 0` を追加してthinkingを無効化すること。これで学習時（非thinking）とサービング時（thinking無効）の整合が取れる。config側にはper-agentで `jinja` / `reasoning_budget` を切り替えられるオプションを追加し、既存の他エージェント（agent_a/b/d）は未指定のまま挙動を変えないようにした（PR #287）。

### 本番検証と、正直に書く運用ミス

デプロイ後の実機検証（16:00）では、起動引数に `--jinja --reasoning-budget 0` が入っていること、本番同形のgrammar付きリクエストで**JSONがpos 0から正しく開始し `finish=stop`、confidence 0.88**（BUY/BUY一致シナリオ）が返ることを確認した。VRAM使用量は6.3GB/12GB、再起動後のエラーは0件。

ここで運用ミスも1つ起きている。デプロイ前のスモークテスト中に実行した `taskkill //IM llama-server.exe` が、プロセス名指定だったために稼働中の本番サーバーも巻き込んで終了させてしまった。約25分間、agent_cの推論が停止し、confidence 0.000（HOLDフォールバック）の状態が続いた。実害は機会損失のみで金銭的損失はなかったが、**PIDを指定したkillにすべきだった**という反省点として残しておく。

なお、meta_analyst（agent_d）は今回のGemma 4切り替えの対象外とした。Gemma 4を2本同時にサーブすると12GBのVRAMに対してOOM（メモリ枯渇）のリスクがあるため、学習パイプラインの実証は完了したものの、agent_dの切り替えは次の週末windowでVRAM設計（部分オフロード等）を検討してから行う判断とした。

## 教訓

1. **文字数ベースの見積もりは検証なしで信じない。** 「日本語はトークン効率が良い」という経験則も、実際にトークナイザで測るまでは仮説にすぎない。`/tokenize` のような実測手段がある場合は、係数を決め打ちする前にまず測る。
2. **似たエラーメッセージでも原因は別ものと疑う。** 「Context size has been exceeded」という文言だけでは、入力長超過なのかKVキャッシュ枯渇なのか判別できない。ソースコードレベルで発生条件を確認しないと誤った層に対症療法を当ててしまう。
3. **フォールバック（grammarを外して再試行）は二次被害を生むことがある。** 一見「壊れないための保険」に見える挙動が、別の資源（max_tokens）を食い潰す新たな失敗経路になり得る。フォールバックそのものが正しく動いているかを疑う。
4. **同型の疾患は過去の事例から学べる。** 今回のagent_c障害は、5週間前にagent_dで確定させたRCA（base選定とデータ形式の不整合）と同じ構造だった。過去の根本原因分析を資産として次のインシデントの仮説生成に使う。
5. **独立レビューは係数の妥当性を検証する場として機能する。** 1人（1エージェント）の判断だけで数値を決めると、極端な方向（今回なら0.8への下げすぎ）に振れるリスクがある。複数の独立した視点で反証し合うプロセスを経ることで、過剰修正を防げた。

## まとめ

約定件数の異常な落ち込みという1つの症状の裏に、独立した3つの層の障害が積み重なっていた。char→token換算係数の算術不足（層1）を直しても、KVキャッシュ枯渇（層2）は別に残り、さらにその奥にはモデルのbase選定とgrammar機構の非互換（層3）という、実は一番大きな根治対象が隠れていた。

層1と層2の対処は「予算を厳密にする」「エラーの種別を切り分ける」という比較的軽い修正で完結したが、層3の根治にはモデルの差し替え（LFM2.5-Thinking → Gemma 4 E2B it 非thinking）という大掛かりな移行が必要で、そこでも4つの独立した罠（peftのモジュール名衝突、mergeのbase推定ミス、配信バイナリの世代遅れ、モデル既定のthinking挙動）を踏んだ。

デモ口座の通算損益は依然-30.5%で、この診断・修正が直接収益を生んだわけではない。この記事が示せるのは「LLMが判断を返せていない」という、収益性以前のインフラ的な健全性を取り戻すまでの過程だけだ。それでも、**症状は1つでも原因が複数層に分かれていることは珍しくない**という点は、ローカルLLMを本番運用する上での一般的な教訓として持ち帰れると考えている。
